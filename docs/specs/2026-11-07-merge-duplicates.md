## 1. 背景与目标

Intake 已能提示疑似重复，但缺少「将 A 并入 B」的产品路径。目标：在确认重复后，把源工作项安全合并到目标工作项，保留可追溯痕迹，并避免数据双写与权限绕过。

## 2. 范围 / 非目标

**范围（P0）**

- 从 Intake 建议或工作项详情发起「合并到…」。
- 选择目标工作项（同项目）；确认后：源关闭/归档为重复，关键信息迁移或摘要到目标。
- 明确迁移字段：描述片段、评论（可选 P0 或 P1）、标签并集、经办人并集策略、附件（P1 可后置）。
- 权限：需对源与目标均有 `issue:edit`（或项目等价权限）。
- 审计：活动流记录「merged into / merged from」与操作者。

**非目标**

- 跨项目合并。
- 自动静默合并（无用户确认）。
- 撤销合并的完整逆向事务（可只留审计链接）。

## 3. 现状对照

| 已有 | 缺口 |
|------|------|
| Intake 重复建议 | 无 merge API / UI |
| Issue 关系 / 活动流 | 无标准 `merged_into` 语义 |

## 4. 功能需求

| ID | 需求 |
|----|------|
| FR-01 | 发起合并：指定源 issue、目标 issue |
| FR-02 | 预检：同项目、非自身、双方可编辑 |
| FR-03 | 确认执行：源标记为重复并指向目标；目标活动流记一笔 |
| FR-04 | 迁移策略文档化并实现最小集（标签并集；描述追加合并摘要） |
| FR-05 | 列表/搜索中源项可识别为已合并（状态或徽章） |

## 5. 验收场景（Given / When / Then）

### AC-01.1 成功合并
Given 同项目两个未合并工作项 A、B，用户对二者有编辑权限  
When 将 A 合并到 B 并确认  
Then A 标记为已合并并关联 B；B 活动流可见合并记录；A 不再作为独立开放项进入默认待办视图

### AC-02.1 拒绝跨项目
Given A、B 分属不同项目  
When 请求合并  
Then 4xx，双方不变

### AC-03.1 无权限
Given 用户对目标无 `issue:edit`  
When 请求合并  
Then 403，双方不变

### AC-04.1 自合并拒绝
Given 源与目标为同一 id  
When 请求合并  
Then 4xx

## 7. 接口与数据约束要点

- 建议：`POST /api/v1/issues/:id/merge` body `{ "target_issue_id": N }`
- 幂等：重复合并已合并源 → 成功或明确 4xx（Design 钉死）
- 事务：迁移与源状态变更同事务

## 8. 风险与开放问题
